# Journal Entry 格式

对 `docs/superpowers/global-dev-journal.md` 中每一条追加 entry，都使用以下结构。

```md
## [YYYY-MM-DD HH:MM] | 阶段：[阶段名]

**阶段说明：**
[用初学者能理解的语言解释这个阶段是做什么的。]

**当前问题：**
[说明当前正在处理的具体问题或目标。]

**当前已知信息：**
[总结已经确认的事实，让用户即使不看 spec 或 plan 也能跟上这条记录。]

**为什么现在做这一步：**
[解释这一步在工作流中的位置，以及为什么它必须先于下一步发生。]

**关键动作：**
[描述真正改变理解或推进工作的那个动作。]

**命令与含义：**
- `[command]`： [解释为什么运行这个命令，以及它提供了什么信号。]

**文件与角色：**
- `[path/to/file]`： [解释这个文件在当前工作流中的职责。]

**技术决策：**
[记录选中的方案，以及为什么其他方案被否决或延后。]

**结果：**
[说明发生了什么、验证了什么、是否仍然存在阻塞。]

**你现在应该理解什么：**
[明确写出这一条希望初学者学到的内容。]

**下一步：**
[写出接下来预期进入的工作流步骤。]
```

## Entry 选择规则

- 每个有教学价值的节点写一条 entry，不要按按键频率写。
- 如果多个重复命令产生的是同一种信号，就合并成一次解释。
- 如果一次测试或检查以新的方式失败，通常值得单独写一条。
- 如果多个细小修改共同支撑了一个决策，就把它们写成一个关键动作。

## 语气规则

- 优先用平实语言，不要堆缩写。
- 先解释为什么，再进入实现细节。
- 每条 entry 要信息密度高，但不要为了显得完整而拉长。
- 默认读者有学习动力，但对工程工作流仍然陌生。
